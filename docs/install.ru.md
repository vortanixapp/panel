## Подготовка к установке

**Состав установки.** Машина панели выполняет саму панель, базу данных и канал
связи с узлами. Игровой узел выполняет игровые серверы. На этапе ознакомления
допускается совмещение ролей на одной машине. При промышленной эксплуатации
роли следует разделять: исчерпание ресурсов игровым сервером не должно
приводить к отказу панели.

| Назначение машины | Минимум | Рекомендуется |
|---|---|---|
| Панель | 2 ГБ ОЗУ, 2 ядра, 20 ГБ диска | 4 ГБ ОЗУ, 4 ядра, 40 ГБ SSD |
| Игровой узел | по требованиям игр | отдельная машина на нагруженную игру |

Сборка образов панели из исходных текстов требует 4 ГБ ОЗУ независимо от
приведённых значений. Настоящий документ описывает установку из готовых
образов, при которой дополнительная память не требуется.

**Архитектура.** Готовые образы собираются только под x86-64 (amd64) — как для
панели, так и для агента. На иных архитектурах, включая arm64, образы требуется
собирать из исходных текстов на целевой машине.

**Доменное имя.** Домен следует подготовить до первого запуска: сертификат
выпускается именно в этот момент. Необходимы два условия:

- A-запись домена указывает на машину панели;
- порты 80 и 443 этой машины доступны из интернета.

Без домена панель работает по IP-адресу и протоколу HTTP. Такой режим допустим
только для ознакомления: учётные данные пользователей передаются по сети
в открытом виде.

**Сетевой доступ.** Машине панели требуются входящие порты 80 и 443. Игровому
узлу входящие порты для работы с панелью не требуются — агент устанавливает
исходящее соединение. Открываются только порты, которые слушают сами игровые
серверы.

## Подготовка машины

```bash
apt-get update && apt-get install -y git curl
```

```bash
curl -fsSL https://get.docker.com | sh
```

Пакет `docker.io` использовать не следует, несмотря на то что Ubuntu предлагает
его при отсутствии команды `docker`. В этом пакете нет плагина Compose:
команда `docker compose` завершается сообщением
`'compose' is not a docker command`, и дальнейшие шаги невыполнимы. Сценарий
выше устанавливает движок, Compose и buildx одновременно.

Проверьте наличие обоих компонентов:

```bash
docker --version && docker compose version
```

При работе не от имени root добавьте пользователя в группу `docker` и откройте
новый сеанс, иначе каждая команда потребует `sudo`:

```bash
usermod -aG docker "$USER"
```

## Установка

```bash
git clone https://github.com/vortanixapp/panel
cd panel
sh scripts/init-env.sh
```

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.images.yml up -d
```

Запускаются восемь контейнеров: PostgreSQL, Redis, API, обработчик очереди,
relay, консоль, веб-интерфейс и Caddy. Порты публикует только Caddy.

Схема базы данных создаётся при первом запуске API. Отдельный шаг применения
миграций не требуется.

Состояние контейнеров:

```bash
docker compose -f deploy/docker-compose.yml ps
```

## Файл deploy/.env и секреты

Сценарий `init-env.sh` создаёт файл `deploy/.env`, генерирует в нём четыре
секрета и задаёт адреса. Значения не выводятся на терминал и не попадают
в историю команд и журналы сервера. Повторный запуск сценария безопасен: он
заполняет только пустые значения и перезаписывает адреса, не затрагивая уже
заданные секреты.

| Переменная | Назначение | Последствия утраты |
|---|---|---|
| `POSTGRES_PASSWORD` | доступ к базе данных | см. примечание ниже |
| `JWT_SECRET` | подпись сеансов | все сеансы завершаются |
| `SECRETS_KEY` | шифрование ключей платёжных шлюзов и учётных данных узлов | расшифровать данные невозможно |
| `INTERNAL_SECRET` | взаимная аутентификация служб панели | службы перестают доверять друг другу |

`POSTGRES_PASSWORD` формируется в шестнадцатеричном виде. Пароль подставляется
в строку подключения; символы `/` и `+`, встречающиеся в base64, нарушают её
разбор, при этом сообщение об ошибке указывает на некорректный порт и не
содержит сведений о пароле.

Значение `SECRETS_KEY` необходимо сохранить отдельно от сервера. Им зашифрованы
ключи платёжных шлюзов и учётные данные узлов. Резервная копия базы данных без
этого ключа неполна: зашифрованные поля восстановлению не подлежат.

Остальные параметры файла описаны в
[`deploy/.env.example`](../deploy/.env.example): почта, вход через внешние
сервисы, реестр образов игр, CORS, проверка обновлений.

## Адрес панели и HTTPS

Ответ на запрос сценария о доменном имени определяет режим работы.

**С доменом** панель отвечает по адресу `https://домен`. Сертификат Let's
Encrypt выпускается при первом запуске, дополнительная настройка не требуется;
продление выполняется автоматически. Если сертификат не выпускается, причиной
почти всегда является одно из двух условий, указанных выше: A-запись или
доступность порта 80.

**Без домена** используется IP-адрес машины и протокол HTTP.

Переход с IP-адреса на домен выполняется двумя командами:

```bash
sh scripts/init-env.sh panel.example.com
```

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.images.yml up -d
```

Иных изменений не требуется. Панель, API, консоль и канал связи с узлами
размещаются на одном адресе и различаются путём запроса, поэтому пути остаются
прежними, изменяется только имя узла. Подключённые игровые узлы получают новый
адрес relay при очередном переподключении.

## Первый запуск

Откройте адрес, выведенный сценарием. Мастер начальной настройки запрашивает
название панели, адрес электронной почты и пароль владельца. Лицензионный ключ
и активация не требуются, передача данных во внешние службы не выполняется.

Созданная учётная запись владельца является единственной с доступом
к административному разделу до тех пор, пока такой доступ не предоставлен
другим пользователям.

Сообщение мастера о том, что панель уже настроена, означает наличие учётной
записи владельца. В этом случае следует выполнить вход.

## Электронная почта

Без настроенного SMTP панель работает, однако подтверждения регистрации,
восстановление пароля и уведомления об оплате не отправляются. Параметры
задаются в `deploy/.env`, после чего требуется перезапуск:

```
SMTP_HOST=
SMTP_PORT=587
SMTP_USER=
SMTP_PASS=
MAIL_FROM=
```

Значение `MAIL_FROM` должно соответствовать адресу, от имени которого SMTP-
сервер разрешает отправку. В противном случае письма принимаются к отправке,
но отклоняются принимающей стороной без уведомления.

Ссылки в письмах формируются на основании `FRONTEND_URL`; это значение задаёт
`init-env.sh`. Если в письмах указан неверный адрес, повторно запустите
сценарий.

## Образы игр

Репозиторий содержит рецепты сборки, но не готовые образы игр. Каталог
`deploy/images` содержит четыре базовых образа среды выполнения, общих для всех
47 игр. Публикация этих образов не выполняется.

Без выполнения описанных ниже действий создание игрового сервера завершается
ошибкой `pull access denied` на этапе загрузки образа.

Соберите образы и опубликуйте их в реестре, доступном игровым узлам:

```bash
VORTANIX_REGISTRY=ghcr.io/your-account sh scripts/build-game-images.sh --runtimes --push
```

Затем укажите тот же реестр в `deploy/.env`, чтобы панель и обработчик очереди
передавали узлам корректный адрес:

```
VORTANIX_REGISTRY=ghcr.io/your-account
```

Добавление новой игры не требует пересборки: игры различаются данными каталога,
а не образами. Полный перечень параметров сценария выводится по команде
`sh scripts/build-game-images.sh --help`.

Для закрытого реестра на каждом узле требуется однократное выполнение
`docker login`.

## Подключение игрового узла

Игровым узлом может выступать любая машина с Linux и Docker. Подготовка
выполняется так же, как для машины панели: установка Docker согласно разделу
[Подготовка машины](#подготовка-машины).

В панели откройте раздел **Администрирование → Локации** и создайте локацию.
Панель выведет готовую команду, содержащую адрес relay, идентификатор узла
и токен. Выполните её на узле. Агент устанавливает исходящее соединение
с relay и удерживает его; открытие входящих портов на узле не требуется.

Узел переходит в состояние «в сети» в течение нескольких секунд. При
отсутствии соединения:

```bash
docker logs vortanix-agent --tail 50
```

Наиболее частые причины: адрес relay недоступен с узла или не разрешается
в DNS; токен был перевыпущен в панели после копирования команды.

Если панель отказывает в выдаче команды и сообщает о незаданном
`RELAY_PUBLIC_URL`, в файле `deploy/.env` отсутствует внешний адрес relay.
Выполните `sh scripts/init-env.sh` повторно и перезапустите панель.

Для развёртывания узлов средствами систем управления конфигурацией каталог
[`deploy/agent`](../deploy/agent) содержит эквивалентные файл Compose
и сценарий. Значения `RELAY_URL`, `AGENT_TOKEN` и `NODE_ID` берутся из панели.

## Резервное копирование

Резервная копия состоит из трёх независимых частей. Наличие только одной из них
не обеспечивает восстановление.

**База данных.**

```bash
docker compose -f deploy/docker-compose.yml exec -T postgres pg_dump -U vortanix vortanix > vortanix-$(date +%F).sql
```

**Значение `SECRETS_KEY`** из `deploy/.env`, сохранённое отдельно. Без него
зашифрованные поля дампа восстановлению не подлежат.

**Загруженные файлы** — изображения оформления и архивы каталога, том
`vortanix_uploads`.

```bash
docker run --rm -v vortanix_uploads:/from -v "$PWD":/to alpine tar czf /to/uploads-$(date +%F).tar.gz -C /from .
```

Файлы игровых серверов размещаются на узлах и в перечисленные копии не входят.
Их резервное копирование выполняется штатными средствами панели, в том числе
во внешнее хранилище, совместимое с протоколом S3. Хранилище настраивается
в разделе **Администрирование → Настройки → Хранилище**; его учётные данные
относятся к числу шифруемых значением `SECRETS_KEY`.

Восстановление базы данных:

```bash
docker compose -f deploy/docker-compose.yml exec -T postgres psql -U vortanix -d vortanix < vortanix-2026-01-01.sql
```

## Версии и каналы обновлений

Переменная `VORTANIX_VERSION` в `deploy/.env` определяет, какие образы
загружает файл наложения.

| Значение | Результат |
|---|---|
| не задано либо `latest` | последний выпуск; изменяется при каждой загрузке |
| `0.1.1` | указанный выпуск и только он |
| `edge` | текущее состояние ветки `main`, пересобирается при каждой отправке |

На машинах, находящихся в промышленной эксплуатации, версию следует
фиксировать явно.

Теги образов не содержат префикса `v`: тегу репозитория `v0.1.1` соответствует
значение `VORTANIX_VERSION=0.1.1`.

Раздел «Обновления» в административной части сообщает о наличии нового выпуска
и содержании изменений. Установку обновления он не выполняет; порядок действий
приведён ниже.

## Обновление

Перед обновлением создайте резервную копию базы данных. Миграции применяются
только в прямом направлении; процедура понижения версии схемы не
предусмотрена, возврат выполняется восстановлением из копии.

```bash
cd panel && git pull
```

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.images.yml pull
```

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.images.yml up -d
```

Команда `git pull` не изменяет состояние работающих контейнеров. Контейнеры
создаются из опубликованных образов; из рабочей копии считываются только
`deploy/.env` и `deploy/Caddyfile`. Новый код доставляет именно команда `pull`.
Её пропуск — наиболее частая причина того, что обновление не даёт результата.

Новые миграции применяются при запуске API. В течение нескольких секунд панель
отвечает с задержкой либо не отвечает.

Если обновление затронуло `deploy/Caddyfile`, перезапустите Caddy явно. Файл
считывается однократно при запуске, а Compose не пересоздаёт контейнер
из-за изменения примонтированного файла:

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.images.yml up -d --force-recreate caddy
```

Игровые узлы обновляются отдельно и не обязательно одновременно с панелью:
агенты сохраняют работоспособность между версиями. Повторное выполнение
команды из раздела **Администрирование → Локации** на узле загружает текущий
образ агента и заменяет контейнер.

## Откат

Если выпуск работает некорректно, укажите в `deploy/.env` предыдущую версию:

```
VORTANIX_VERSION=0.1.0
```

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.images.yml up -d
```

Такой откат применим лишь в случае, когда покидаемый выпуск не применял
миграций. В противном случае прежний код обращается к схеме, которая ему
неизвестна, и корректный порядок действий следующий:

1. остановить стек командой `docker compose … down`;
2. восстановить дамп базы данных, созданный до обновления;
3. указать прежнее значение `VORTANIX_VERSION` и запустить стек.

По этой причине резервное копирование предшествует обновлению.

## Работа за сторонним обратным прокси

В состав панели входит Caddy, занимающий порты 80 и 443 и обеспечивающий
выпуск сертификата. Если завершение TLS выполняется другим сервером, задайте
в `deploy/.env` свободные значения `HTTP_PORT` и `HTTPS_PORT`, направьте на них
собственный прокси и сохраните маршрутизацию по путям:

| Путь | Назначение |
|---|---|
| `/v1/agent/*` | игровые узлы, WebSocket |
| `/v1/console`, `/v1/dashboard` | консоль сервера, WebSocket |
| `/v1/*` | API |
| остальное | веб-интерфейс |

Прокси без поддержки протокола WebSocket приводит к отказу консоли и связи
с узлами при работоспособности остальных функций.

После настройки выполните `sh scripts/init-env.sh домен`, чтобы адреса,
передаваемые узлам и указываемые в письмах, соответствовали фактическому.

## Эксплуатация

Все команды требуют обоих параметров `-f`, поэтому целесообразно определить
псевдоним:

```bash
alias vx='docker compose -f ~/panel/deploy/docker-compose.yml -f ~/panel/deploy/docker-compose.images.yml'
```

| Задача | Команда |
|---|---|
| Состояние контейнеров | `vx ps` |
| Журнал API в реальном времени | `vx logs -f api` |
| Перезапуск отдельной службы | `vx restart api` |
| Остановка | `vx down` |
| Запуск | `vx up -d` |
| Консоль базы данных | `vx exec postgres psql -U vortanix vortanix` |
| Использование дискового пространства | `docker system df -v` |

После инициализации API отвечает на запрос `GET /health`; этот адрес пригоден
для внешнего мониторинга.

## Диагностика

```bash
docker compose -f deploy/docker-compose.yml ps
```

```bash
docker compose -f deploy/docker-compose.yml logs api
```

- **Контейнер `api` циклически перезапускается.** Причина указана в его
  журнале. Как правило, это незаданный `POSTGRES_PASSWORD` либо недоступная
  база данных.
- **Панель открывается, но все запросы завершаются ошибкой.** Браузер
  обращается к API по адресу, который не обслуживается. Выполните
  `sh scripts/init-env.sh` с фактическим адресом и проверьте, что он указан
  в `CORS_ORIGINS`.
- **Мастер настройки сообщает, что панель уже настроена.** Учётная запись
  владельца существует. Выполните вход либо удалите том базы данных и
  начните заново командой `docker compose down -v`, которая уничтожает все
  данные.
- **Сертификат не выпускается.** A-запись не указывает на эту машину либо
  закрыт порт 80: проверка Let's Encrypt выполняется по порту 80 в том числе
  для сертификата HTTPS. Конкретная причина указана в выводе
  `docker compose logs caddy`.
- **После изменения `POSTGRES_PASSWORD` API не подключается к базе.** Пароль
  задаётся PostgreSQL однократно, при создании каталога данных. Изменение
  переменной меняет пароль, передаваемый панелью, но не ожидаемый базой.
  Измените пароль в самой базе командой `ALTER USER vortanix WITH PASSWORD '…'`
  либо удалите том и выполните установку заново.
- **Создание сервера завершается ошибкой `pull access denied`.** Образы игр
  не собраны и не опубликованы, см. раздел [Образы игр](#образы-игр).
- **Машина перестала отвечать во время сборки с параметром `--build`,
  включая SSH.** Сборке веб-интерфейса не хватило оперативной памяти. Ошибка
  при этом не выводится: система переходит к интенсивному использованию
  подкачки и перестаёт отвечать. Завершение сеанса SSH сборку не
  останавливает, поскольку она выполняется демоном Docker. Перезагрузите
  машину средствами панели управления хостинг-провайдера и используйте готовые
  образы. Если сборка на машине с малым объёмом памяти необходима,
  предварительно добавьте раздел подкачки:

  ```bash
  fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
  ```

## Удаление

Остановка с сохранением данных:

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.images.yml down
```

Остановка с удалением базы данных, Redis, загруженных файлов и сертификата.
Операция необратима:

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.images.yml down -v
```

На каждом игровом узле:

```bash
docker rm -f vortanix-agent
```

Файлы игровых серверов остаются в каталоге `/var/lib/vortanix/servers` до тех
пор, пока не будут удалены вручную.
